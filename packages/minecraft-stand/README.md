# Minecraft-стенд

Версия 0.2.0 — самостоятельное ядро выделяемого стенда (#426). Node.js ≥22, без внешних npm-зависимостей,
Firebase, git или настроек TFC. Каталог пакета можно установить отдельно от tfc-plans.

Реализованы фиксация и перенос входов, проверка версии инструмента, изолированная подготовка каждого шага,
JVM-процесс, проверки, сохранение артефактов и уборка. Оба вида шагов используют один lifecycle.
Адаптеры NeoForge/клиентского экрана и подключение новой модели к установленной очереди ещё выделяются;
текущие MCP-команды продолжают работать через прежний адаптер `legacy-args`.

## Команды

```sh
node cli.mjs identity
node cli.mjs validate job.json
node cli.mjs freeze spec.json --store ./sender
node cli.mjs transfer <SHA256 задания> --from ./sender --into ./worker-store
node cli.mjs run <SHA256 задания> --store ./worker-store --work ./work --out ./results --worker ./worker.json
```

`identity` печатает версию и SHA256 установленного runner по его коду и package.json. Устанавливайте каждый выпуск
в отдельный неизменяемый каталог; обновление каталога во время прогона не поддерживается. Worker и runner сейчас
выпускаются одним пакетом, но в паспорте представлены отдельно; worker может предоставить собственную identity.

`freeze` читает спецификацию с локальными входами и возвращает закреплённое задание и его `ref.sha256`.
Вместо SHA256 можно указать `{ "directory": "./каталог" }` для дерева сборки, кандидата, дистрибутива или мира.
Сценарий допускает `{ "file": "./scenario.json" }` или `{ "inline": { … } }`.
Относительные пути считаются от спецификации. Если runner не указан, фиксируется текущая установленная версия.
Изменение или удаление локальных исходников после фиксации не меняет входы прогона.

`transfer` переносит транзитивное замыкание входов, проверяя хеш каждого файла. Передаётся содержимое задания,
без репозитория или исходников инструмента. Runner устанавливается отдельно. Один SHA256 можно передавать и запускать
повторно: каждый `run` создаёт новый идентификатор и свежие среды, а входы остаются прежними.
Идемпотентная постановка и повторная доставка запросов относятся к очереди, а не к прямому `run`.

Пример `worker.json`: `{ "memoryMiB": 16384, "capabilities": ["java21", "display"] }`.
Это объявление ресурсов установленной службы. Требования задания проверяются до запуска; JVM получает `-Xmx`
из `resources.memoryMiB`. ОС, архитектура и системные библиотеки должны соответствовать закреплённым дистрибутивам.
Ядро изолирует каталоги, но не является контейнером или средством запуска недоверенного кода.

## Задание

Ниже спецификация для подготовленного server tree NeoForge. Все файлы установки загрузчика, библиотеки,
конфиги и аргументы должны быть в перечисленных деревьях. Команда не скачивает недостающие файлы и не запускает
установщик из сети. Отдельные адаптеры подготовки/получения дистрибутивов добавляются следующим этапом.

```json
{
  "schemaVersion": 1,
  "id": "server-restart",
  "basePack": { "directory": "./pack" },
  "candidate": { "directory": "./candidate" },
  "environment": {
    "minecraft": { "version": "1.21.1", "distribution": { "directory": "./minecraft" } },
    "loader": { "version": "neoforge-21.1.256", "distribution": { "directory": "./neoforge" } },
    "java": { "version": "21", "distribution": { "directory": "./jdk21-linux" } }
  },
  "resources": { "memoryMiB": 8192, "capabilities": ["java21"] },
  "limits": { "prepareSeconds": 600, "totalSeconds": 1800 },
  "steps": [
    {
      "id": "build",
      "kind": "server",
      "backend": "jvm",
      "after": [],
      "timeoutSeconds": 600,
      "launch": { "args": ["@libraries/net/neoforged/neoforge/21.1.256/unix_args.txt", "nogui"] },
      "scenario": {
        "inline": { "readyText": "Done (", "commands": ["save-all flush"], "holdSeconds": 2, "stopCommand": "stop" }
      },
      "checks": [{ "id": "saved", "type": "file-exists", "path": "world/level.dat" }],
      "artifacts": ["logs", "world"]
    },
    {
      "id": "restart",
      "kind": "server",
      "backend": "jvm",
      "after": ["build"],
      "world": { "fromStep": "build" },
      "timeoutSeconds": 600,
      "launch": { "args": ["@libraries/net/neoforged/neoforge/21.1.256/unix_args.txt", "nogui"] },
      "scenario": { "inline": { "readyText": "Done (", "stopCommand": "stop" } },
      "checks": [{ "id": "ready", "type": "log-contains", "text": "Done (" }],
      "artifacts": ["logs", "world"]
    }
  ]
}
```

После `freeze` локальные ссылки заменяются SHA256 manifest каждого дерева и сценария. Сборка и кандидат имеют
разные хеши. В установленной версии должны совпадать версия и SHA256 runner. Каждый шаг материализует отдельную
Java и накладывает деревья Minecraft → loader → сборка → кандидат в отдельный game dir. Кеш содержит только
проверяемые файлы; материализация повторно проверяет SHA256 и создаёт независимые копии, без hardlink/symlink.

Деревья содержат пути, размер, SHA256 и признак исполняемого файла. Внутренняя ссылка на обычный файл JDK
фиксируется его байтами; ссылки наружу, ссылки на каталоги и специальные файлы отклоняются.
Повреждённый кеш даёт отказ до исполнения соответствующего шага. Повторный `transfer` может восстановить его
из исходного неизменённого хранилища.

Шаги перечисляются в топологическом порядке; `after` ссылается только на предыдущие шаги. Каждый шаг зависит
от успешной приёмки перечисленных предшественников. Мир передаётся как закреплённое дерево сохранённого выхода
`world`; у источника он должен быть объявлен в `artifacts`. Можно задать независимый `world.input`.
При передаче убирается `session.lock`. Проваленный шаг блокирует зависимые; остальные независимые шаги продолжаются.

## Backend и приёмка

Установленные адаптеры регистрируются в `backends.mjs` и входят в SHA256 runner. Сейчас доступен `jvm` для обоих
видов шага; это запуск подготовленной Java-команды, а не автоматический Minecraft launcher.
Он использует закреплённую Java `bin/java` (или относительный `launch.java`), `launch.jvmArgs` и `launch.args`.
В аргументах доступны `${game}`, `${java}`, `${memoryMiB}`. Shell не вызывается. Чувствительные переменные службы
не передаются JVM. Сетевые права ОС не ограничиваются ядром; полный набор входов позволяет работать без сети,
но конкретные моды могут сами обращаться к внешним сервисам.

JSON-сценарий ожидает `readyText`, отправляет строки `commands` в stdin, затем через `holdSeconds` отправляет
`stopCommand`. `stopAfterReady` останавливает группу сигналом, что само по себе не считается успешным выходом.
Readiness добавляет отдельную проверку. Сценарии нового типа реализуются адаптером из состава установленного runner.

Общие проверки: `process-exit` (код по умолчанию 0), `log-contains` / `log-absent` (буквальный `text` по stdout/stderr),
`file-exists` (относительный `path` внутри game). Каждый шаг требует явных проверок. Код процесса хранится отдельно
от приёмки; код 0 не скрывает провал проверки. JVM backend сохраняет выходы `logs`, `world`, `frames`
из `game/logs`, `game/world`, `game/screenshots`. Отсутствие запрошенного артефакта проваливает приёмку.

Стадии отражаются в `events.jsonl`: validate → prepare → execute → check → archive → cleanup → finished.
Подготовка имеет отдельный timeout, выполнение — timeout шага, весь прогон — общий timeout.
После отмены/общего timeout артефакты сохраняются с отдельным бюджетом `limits.archiveSeconds` (по умолчанию 60 с),
после чего среда убирается; прогон при этом остаётся проваленным. SIGINT/SIGTERM
CLI отменяет подготовку/процесс. При остановке завершается вся группа процессов, с SIGKILL после льготного срока.
Журнал процесса ограничен 64 MiB; превышение даёт ошибку. Рабочие каталоги убираются при успехе, отказе и отмене.

Результаты: общий `passport.json`, `result.json`, события; по каждому шагу — полный ограниченный stdout/stderr,
свой `result.json`, закреплённые деревья и копии объявленных артефактов. Результат различает исход процесса,
проверки и `passed` / `failed` / `unknown`. Ошибка уборки также проваливает прогон.

## Совместимость и проверенный объём

Старая очередь сохраняет `passport.json` и `result.json` через `legacy-args`. Её worker identity описывает чистый
checkout revision, а не независимый дистрибутив. Без отдельного протокола проверок прежний код 0 даёт `unknown`
в новом результате; ответы MCP и старые правила цепочек сохранены. Старым заданиям паспорт не добавляется задним числом.

Автономные проверки ядра с настоящей Java-программой покрывают холодный/тёплый кеш, неизменность кандидата,
передачу файлов мира, повторы, отрицательную приёмку, timeout, отмену процесса/подготовки, ограничения возможностей,
версию runner, повреждение кеша и обход пути. Это инфраструктурный fixture, не приёмка реальной Minecraft-сборки.
Последняя остаётся открытой в #426 вместе с миграцией MCP/очереди и выделением TFC/NeoForge/печати схем в адаптеры.
