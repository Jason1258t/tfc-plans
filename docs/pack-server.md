# Сервер сборки

Сервер, который хранит сборку игры и раздаёт её программе [`tfc`](tfc-app.md). Он же сам собирает из сборки данные
сайта (предметы, рецепты, карту, разбор KubeJS) и выкладывает их на сайт. Пересобрать данные и обновить сайт можно
с любого устройства, ПК с Minecraft для этого не нужен.

- Код — [server/pack-server/](../server/pack-server/). Полная справка (установка с нуля, все настройки, API) —
  [server/pack-server/README.md](../server/pack-server/README.md).
- Зачем так устроено и порядок работ — [plans/pack-cli.md](plans/pack-cli.md). Что сделано и что ждёт решения —
  [plans/pack-cli-summary.md](plans/pack-cli-summary.md).

## Как это работает

- **Снимок** — версия сборки. Это список файлов (путь, контрольная сумма, размер), а сами файлы хранятся по
  одному разу. Поэтому одинаковый jar в десяти версиях занимает место один раз, а обновление сборки — десятки МБ.
- **Текущий снимок** — то, что получают игроки по `tfc sync`. Откат — переключение на прошлый снимок, ничего
  не удаляется.
- **Ключи.** Моды раздаются только своим, поэтому без ключа сервер отвечает только на `/health`.
  - Роль `player` — качать сборку.
  - Роль `admin` — заливать, переключать, выдавать ключи, публиковать на сайт.
  - На сервере хранится только хеш ключа: ключ показывается один раз при выдаче.
- **Белый список путей.** В снимок принимаются:
  - `mods/`, `config/`, `defaultconfigs/`, `serverconfig/`, `kubejs/`, `resourcepacks/`;
  - из мира — `datapacks/` и календарь TFC.

  Никогда не принимаются `server.properties`, списки игроков (ops, whitelist, баны), данные игроков, регионы мира
  и логи (в логах — адреса игроков). Снимок с таким путём отклоняется целиком.

### Что происходит после `tfc publish`

1. Программа хоста заливает только те файлы, которых на сервере ещё нет, и создаёт снимок.
2. Снимок становится текущим, и игроки получают его по `tfc sync`.
3. Сервер ставит в очередь задание **сборки данных сайта**. Оно идёт отдельным процессом, по одному за раз.
4. Затем **публикация**: сервер сравнивает собранное с тем, что сейчас на сайте.
   - **Сейчас она пробная:** сервер только показывает, что изменилось бы.
   - Настоящая выкладка — по команде хоста `tfc admin publish --live`.
   - Выкладывается только изменённое: файлы данных на Hosting, настройки сборки в Firestore `config`
     и запись в «Обновления сборки», если поменялись моды, предметы или рецепты.
   - Сам сайт, аддоны и ресурспаки остаются такими, как их выложил разработчик.

Ход заданий — `tfc admin jobs`, подробнее — в [инструкции программы](tfc-app.md#хосту).

### Что ещё раздаёт сервер

- **Собранные данные снимка** (`/data`). Отсюда их берёт сборка сайта на машине без jar (`TFC_PACK_URL` и
  `TFC_PACK_TOKEN` в `.env.local`) и `npm run pack:fetch`.
- **Контент сайта для `tfc pull`** (`/site/…`): датапаки с отметкой «Ставить в мир», скрипты KubeJS с отметкой
  «Ставить на сервер», библиотека схем.
  - Сам сайт закрыт App Check, поэтому программа берёт этот контент здесь, а сервер читает Firestore своим
    сервисным ключом.
  - Списки кешируются на 5 минут, чтобы не тратить бесплатный лимит чтений.

Токен DuckDNS и сервисный ключ лежат **только на сервере**: не в git, не в чате и не в общих папках.
Если копия сервисного ключа осталась в «Загрузках» на ПК — удалите её.

### Чужие службы на машине — не трогать

На VPS уже работают другие службы, и они важнее нашей:

- прокси Telegram (Docker) на 443;
- Xray на 6080, 6443, 6444 и 8080; порт 8443 зарезервирован под Xray;
- бот;
- raven-subscribe на 47291;
- правило ufw на 6000.

Поэтому HTTPS сервера сборки — не на 443, а на 28788, и порт 80 не открывается: сертификат выдаётся через DNS.

Прежде чем открывать новый порт, проверьте его:

- `ss -tulnp` — кто что слушает;
- `ufw status`;
- `iptables -t nat -S`;
- конфиг Xray;
- `history` пользователя root.

### Обслуживание

```bash
ssh tfc 'systemctl status tfc-pack caddy --no-pager'   # работают ли
ssh tfc 'journalctl -u tfc-pack -n 100 --no-pager'     # лог: каждая заливка, снимок, ключ — строка с именем ключа
ssh tfc 'df -h / && free -m'                           # место и память
```

**Обновить код сервера** после слияния в `main`:

```bash
ssh tfc 'cd /opt/tfc-plans && git pull && bash server/pack-server/deploy/install.sh'
```

- Без домена в аргументах скрипт только обновляет код и перезапускает службу. Настройки, сборку и ключи он
  не трогает.
- Код разборщиков для сборки данных сайта — отдельная копия репозитория в `/var/lib/tfc-pack/repo`.
  Её подтягивает `tfc admin rebuild --pull`.

**Ключи** удобнее выдавать из программы: `tfc admin invite <ник>`, `tfc admin keys`, `tfc admin revoke <id>`.
Без программы — прямо на сервере (`node cli.mjs key …` в `/opt/tfc-pack`, см.
[README сервера](../server/pack-server/README.md#ключи)). Последний ключ администратора отозвать нельзя.

**Бэкап** — копия папки `/var/lib/tfc-pack`. Сейчас он не настроен.

**Настройки** (`/etc/tfc-pack.env`) после правки применяются через `systemctl restart tfc-pack`. Главные:

| Настройка                        | Что значит                                                                          | Сейчас                     |
| -------------------------------- | ----------------------------------------------------------------------------------- | -------------------------- |
| `AUTO_BUILD`                     | собирать ли данные сайта после смены текущего снимка                                | не задана (`on`)           |
| `AUTO_PUBLISH`                   | после сборки: `dry-run` — только показать, `live` — сразу выложить, `none` — ничего | не задана (`dry-run`)      |
| `BUILD_HEAP_MB`                  | лимит памяти процесса сборки                                                        | 640 (сборка берёт ~0,9 ГБ) |
| `GOOGLE_APPLICATION_CREDENTIALS` | сервисный ключ Firebase для публикации и `/site`                                    | задан                      |

### Память

Сборка данных модов берёт до ~0,9 ГБ при свободных ~1,0 ГБ, а свопа на машине нет. Если сборку убьёт нехватка
памяти, в задании так и будет написано. Тогда нужен своп (около 2 ГБ на диске). Создавать его — только с согласия
хоста: машина общая.

## Запустить у себя для разработки

```bash
cd server/pack-server
npm run key -- add host --role admin   # ключ администратора в ./data/keys.json
npm run dev                            # http://127.0.0.1:8788, данные — ./data
```

Программа к нему: `tfc login <ключ> --server http://127.0.0.1:8788`. Сборку данных такой сервер запускает из этого
же репозитория. Пробная публикация читает Firebase от имени `firebase login`.
