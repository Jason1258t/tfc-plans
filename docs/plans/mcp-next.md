# MCP сборки: следующие инструменты

Заказ по итогам работы над аддоном EE Extras 2.0 (2026-10-21): что агент делал руками (`unzip`, `javap`, декомпиляция
целых классов, разовые скрипты), хотя это могли бы сделать инструменты MCP. Устройство MCP и как добавлять
инструменты — [../mcp.md](../mcp.md). Статус: пункты ① — **сделано** (2026-10-21), остальные — **не начато**.

Приоритет — по тому, сколько времени и ошибок экономит: ① — сразу, ② — следующим заходом, ③ — когда будет повод.

## ① Рецепты с датапаками сайта

**Статус: сделано** (2026-10-21) — `scripts/mcp/site-datapacks.mjs`; `recipes_for electroenergetics:duplex_wire_spool`
находит рецепт датапака `electroenergetics_missing`.

**Что:** `recipes_for` / `recipes_using` / `recipe_get` должны учитывать датапаки сайта, отмеченные «ставить»
(Firestore `datapacks`, `install = true`), как ещё один слой поверх модов и KubeJS (порядок — как в мире: датапаки
мира поверх модов, KubeJS удаляет рецепты и из них).

**Зачем:** `recipes_for electroenergetics:duplex_wire_spool` ответил «ничего не найдено», хотя рецепт есть
в датапаке `electroenergetics_missing`. Агент чуть не решил, что крафта нет.

**Как:** при первом запросе — одно чтение коллекции `datapacks` (сейчас 9 документов), кеш на сессию со сбросом по
времени; разбор записей — тем же `src/lib/datapackFiles.ts`, что и сайт. В ответе помечать источник «датапак сайта
<имя>». Записи с `install = false` — отдельной строкой «есть на сайте, не ставится».

## ① Модель и текстура картинкой

**Статус: сделано** (2026-10-21) — `model_render`, `texture_get` (`scripts/mcp/render.mjs`, `resources.mjs`). При
переносе нашлась ошибка `iso.py`: отсечение граней было перевёрнуто — рисовались задние грани (у печи не видно
лица). В MCP исправлено; иконки аддона на сайте, сделанные `iso.py`, стоит перерисовать.

**Что:** `model_render(id, state?, view?)` — блок или предмет из jar, KubeJS или папки аддона (`tools/<мод>/src/main/resources`)
в PNG: блокстейт → модель (с `parent`, поворотами x/y, `uv`, `rotation` грани и элемента) → объёмная картинка как в
инвентаре или вид сверху. `texture_get(path, scale?)` — текстура из jar картинкой, плюс палитра (частые цвета с долями).

**Зачем:** чтобы нарисовать блоки в стиле EE, агент распаковывал текстуры и считал палитру скриптом, а свои модели
проверял рендером `tools/ee-extras-mod/art/iso.py` (без поворотов элементов, без `parent`). Запуск клиента ради
проверки модели на этой машине невозможен (нет монитора для GLFW из песочницы).

**Как:** перенести растеризатор `iso.py` в `scripts/mcp/` на Node (PNG — уже есть в `scripts/`), добавить `parent`,
повороты элементов, `display.gui`. Ответ — картинка (MCP `image` content), чтобы агент её видел.

## ① Проверка ресурсов без клиента

**Статус: сделано** (2026-10-21) — `resources_check`. EE Extras — ошибок нет. В EE 1.1.2 нашлась пропажа
`electroenergetics:block/duplex_wire_segment` (на неё ссылается `CEEPartialModels`, её же берёт оболочка
двухпроводного кабеля EE Extras) — по jar, в игре не проверялось.

**Что:** `resources_check(mod | path)` — то, что клиент проверяет при загрузке: у каждого блока есть блокстейт, его
варианты покрывают все сочетания свойств блока, модели и текстуры существуют (с учётом `parent` и чужих
namespace), у предметов есть модель, ключи перевода, которые встречаются в коде (`ldc` с `block.`, `item.`,
`<modid>.`), есть в `ru_ru` и `en_us`, `PartialModel.of(...)` указывает на существующую модель.

**Зачем:** ошибки ресурсов аддона сейчас видны только в игре у игрока. Свойства блока (FACING, ROLL, FLIP у
наследников чужих блоков) агент выписывал из байткода руками, и ошибка в блокстейте прошла бы незамеченной.

**Как:** свойства — из байткода (`classfile.mjs`): `createBlockStateDefinition` и цепочка предков, значения enum —
из классов свойств. Для папки аддона — читать `build/classes` и `src/main/resources`.

## ② Устройства Electro Energetics: клеммы и провода

**Что:** `ee_device(block)` — для блока EE: класс устройства, контакты (id, координаты в пикселях для каждого
положения, подпись, доступен ли для провода, скрытые узлы), что устройство ставит в цепь (`preTick`: резисторы,
источники, диоды — по байткоду), какие настройки EE использует. `ee_wire_types()` — все типы проводов: сопротивление,
изоляция, предельное напряжение и нагрев, длина, декоративный ли, чем выпадает и какая катушка (с подстановкой
значений из конфига).

**Зачем:** раскладку узлов двухпроводного соединителя (`0x1000 | сторона << 4 | жила`, четыре стороны по FLIP и ROLL)
и типы проводов агент собирал из трёх декомпилированных классов. Нужно и для справочника «power», и для каждого
следующего аддона к EE.

**Как:** `NodeConfigurator.Builder.add(...)` в `<clinit>` и методах блока — константы из байткода (как
`scripts/mods/power.mjs`); повороты — те же, что проверяет `tools/ee-extras-mod/art/CheckNodes.java`.

## ② Возможности блоков (capabilities) по сторонам

**Что:** `capabilities_of(block | blockEntity)` — какие возможности NeoForge (энергия, жидкости, предметы)
регистрирует мод для блока, с какой стороны они есть и с какими ограничениями (только вход, только выход,
настраиваемые стороны — как у конденсатора IE `IOSideConfig`), предельные потоки из конфига.

**Зачем:** что грань конденсатора IE бывает либо входом, либо выходом, и что преобразователь EE отдаёт FE только
через заднюю грань, агент выяснял декомпиляцией — от этого зависела вся схема двустороннего преобразователя.

**Как:** найти обработчики `RegisterCapabilitiesEvent` (уже умеет `event_listeners`), разобрать
`registerBlockEntity/registerBlock` и лямбду-провайдер: проверки `side`/`context`. Где разбор не удался — честно
вернуть «смотри decompile <класс>#<метод>».

## ② Сцены Ponder и подсказки модов

**Что:** `ponder_search(query)` / `ponder_get(item)` — сцены Ponder (Create, EE и аддоны): к каким предметам, тексты
шагов по-русски и по-английски. Плюс подсказки предметов из перевода (`*.tooltip*`).

**Зачем:** у EE нет книги — его документация это Ponder. Сейчас агент ищет `ponder.` в `lang_search` и сам
сопоставляет сцены с блоками; `book_search` Ponder не индексирует (см. ../mcp.md, «Книги модов»).

**Как:** регистрация сцен — `PonderPlugin`/`registerScenes` в байткоде (id сцены → теги предметов), тексты — ключи
`<ns>.ponder.<сцена>.*` в lang. Индекс — как у книг, в памяти.

## ③ Конфликты рецептов

**Статус: сделано** (2026-10-24) — `recipe_conflicts` (`scripts/mcp/tools/recipes.mjs`).

**Что:** `recipe_conflicts(recipe JSON | ingredients)` — есть ли в сборке (моды, KubeJS, датапаки сайта) рецепт того
же типа с теми же входами (бесформенный — тот же набор, shaped — та же сетка с учётом зеркала и тегов), который
перехватит новый.

**Зачем:** для изоляторов агент вручную подбирал рецепты «1 изолятор → двухжильный, 2 → четырёхжильный», чтобы они
не перехватывали друг друга и рецепты EE. То же нужно при каждом новом датапаке на сайте.

## ③ Прогон сервера разработки аддона

**Статус: сделано** (2026-10-24) — `addon_devserver` (scripts/mcp/tools/devserver.mjs).

**Что:** `addon_devserver(addon, commands[], env?)` — запустить `tools/<мод>/test-server.sh` с командами и вернуть
ответы RCON по командам, ошибки и исключения из лога (через `log_analyze`).

**Зачем:** сегодня ~10 запусков вручную, вывод каждый раз фильтровался `grep`. Запуск долгий (минута-две) —
инструмент должен честно ждать и возвращать короткий итог.

**Как:** обёртка над скриптом аддона; запускать только по прямому вызову, не в фоне.
