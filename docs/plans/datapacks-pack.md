# Датапаки на уровне сборки — dev #125

Общий фикс подключается ко всем мирам через ZIP в `kubejs/data/`. Мир остаётся местом проверки новых версий.
Подтверждает версию хост после проверки в игре: само наличие ZIP или отметка карточки этого не означает.

## Подключение и приоритет

Проверено по коду **KubeJS NeoForge 2101.7.2-build.368** из снимка сборки:

- `ServerScriptManager.createPackResources` вызывает `KubeFileResourcePack.scanAndLoad(KubeJSPaths.DATA, …)`.
- Загружаются ZIP непосредственно в `kubejs/data/`; вложенная папка внутри ZIP не нужна, в корне — `pack.mcmeta`.
- ZIP сортируются по имени без учёта регистра. Поздний ZIP перекрывает ранний по одному пути ресурса.
- ZIP вставляются после обычных `FilePackResources` (ZIP мира); затем идут прямые файлы `kubejs/data/<namespace>/`.
  Прямые данные KubeJS имеют более высокий приоритет, чем ZIP сборки. Финальные виртуальные данные и обработка
  рецептов скриптами KubeJS продолжают действовать.
- Механизм применяется при создании ресурсов сервера, поэтому предназначен для старых и новых миров. Новый мод
  не требуется. Фактическое подключение, старый/новый мир и приоритеты **в игре не проверялись**.

Сборщики сайта читают ZIP в том же порядке; рецепты, поддерживаемые данные TFC/еды/топлива/руд и MCP loot
учитывают архивы. Старые ограничения справочников остаются: например, произвольные теги датапака и некоторые
данные модов ещё не индексируются полностью. Отдельный каталог данных не доказывает работу рецепта в игре.

## Учёт и переход

Источник истины — текущий снимок сервера сборки. Поле `datapacks` содержит id, имя, путь ZIP, sha256 архива,
хеш содержимого (не зависит от сжатия/даты ZIP), ревизию источника, автора и дату подтверждения, известные пути
копий мира. Данные сайта в Firestore не переписываются. Для ZIP снимка без карточки сайта id выводится из хеша
содержимого; сохраняется исходный filename. Неизвестные/повреждённые ZIP явно видны в списке.

`confirm` сверяет локальную копию мира с исходником сайта или ZIP текущего снимка. На сервер сначала попадают
байты ZIP, затем создаётся новый снимок с файлами и подтверждениями; переключение защищено проверкой базового
снимка. Конфликт ревизии карточки, прав, содержимого или параллельная смена снимка дают отказ. Пересечение разных данных по одному пути в выбранных
и уже установленных ZIP также блокирует перенос: сначала нужно устранить разные копии или согласовать порядок. До успешного
переключения файлы хоста не меняются. После него CLI догружает выбранные пакеты в сборку и убирает совпавшие
дубли мира с резервной копией. Изменённые и неизвестные копии сохраняются с сообщением.

Сбой локальной догрузки после подтверждения: повторить `tfc pull datapacks`. Подтверждение на сервере уже есть;
пакеты не дублируются. Обычный `publish` сохраняет подтверждённые файлы даже у старого клиента или старого профиля.
Их замену делают через снятие подтверждения и новую проверку, а не случайной заливкой всей папки.

Архивы сохраняют тип `kubejs` в снимке: прежний CLI получает их обычным `tfc pull`, в том числе без выбранного мира.
Подтверждённые карточки исключены из `/site/datapacks` даже для старого CLI, поэтому он не устанавливает новые
копии в мир. Для адресных команд, очистки ручных дублей и диагностики следует обновить программу.

Метаданные подтверждений публикуются в `kubejs.json` вместе с рецептами того же снимка. Сайт и MCP показывают
**опубликованный** снимок; до окончания сборки/публикации сведения могут отставать от CLI, который читает сервер.
Правка карточки после подтверждения не обновляет сборку автоматически. Снятие отметки установки на сайте тоже
не отменяет уже подтверждённый фикс. Для ZIP без карточки источником служит опубликованный снимок, не Firestore.

## Команды хоста и игрока

```bash
tfc datapacks list                     # сайт, локальные ZIP и снимок: состояния, id, хеши, места
tfc datapacks files                    # filename — название для ZIP снимка (сопоставление по содержимому)
tfc datapacks list бетон               # поиск; для неоднозначного выбора используйте id
tfc datapacks install all              # отмеченные ещё не подтверждённые → выбранный мир; подтверждённые → сборка
tfc datapacks install "Фикс магмы"      # один, в том числе тестовый или ZIP снимка по filename
tfc datapacks confirm all --dry-run    # план: только присутствующие в мире совпадающие версии
tfc datapacks confirm "Фикс магмы" --yes # после проверки в игре — один для всей сборки
tfc datapacks confirm all --yes        # после проверки — все подходящие, включая ZIP снимка
tfc datapacks unconfirm "Фикс магмы" --yes # обратно в мир для проверки новой редакции
tfc pull datapacks --dry-run           # общий план синхронизации
tfc undo                              # только локальные файлы и state; серверный снимок не меняет
tfc admin rollback                    # серверный откат всего снимка; после него tfc pull datapacks
```

`confirm` и `unconfirm` требуют ключ администратора, показывают план и запрашивают подтверждение (или `--yes`).
`install` требует выбранного мира; обычный `pull` доставляет пакеты сборки и без мира. `all` при подтверждении
пропускает отсутствующие, тестовые неотмеченные и повреждённые ZIP с объяснением; один выбранный пакет при
несовпадении даёт ошибку. Команды принимают id, точное имя, filename; при одинаковых именах нужен id.
Подтверждаются ZIP с `pack.mcmeta` в корне; папку датапака сначала нужно упаковать и опубликовать в снимке.

`unconfirm` сохраняет проверенную копию в снимке мира; следующий `pull` может заменить её более новой редакцией
карточки сайта. Проверить её в игре, затем подтвердить заново. Изменённый вручную ZIP сборки не удаляется молча:
новый ложится рядом как `.tfc-new`; хост должен разобраться с оставшейся копией до проверки в игре.

Резервные копии — `.tfc/backup/`, последние пять операций. `undo` отказывается восстанавливать файлы мира, если
в профиле уже выбран другой мир. Серверный откат касается всего снимка, а не только одного датапака.
