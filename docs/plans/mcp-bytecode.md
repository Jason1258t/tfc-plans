# План: сжатый разбор байткода в MCP (`bytecode`)

Задача на сайте: yNJibIuWW9TDZ8xmuFlN. Ветка `feat/mcp-bytecode`, worktree `.claude/worktrees/mcp-bytecode`.

## Что показала история сессий (85 транскриптов)

- После появления MCP (2026-10-21) «разбор по байткоду» — в основном `decompile`: ~380 вызовов, в среднем 3,8 тыс.
  символов. Целый класс — 200 вызовов по ~5,4 тыс. (41 больше 8 тыс.); с `method=` — ~2,2 тыс. Один и тот же
  класс/метод повторно в одной сессии — 59 раз.
- `javap` через терминал всё ещё ~25 раз в день (всего 320 вызовов, 1,6 млн символов). Почти всегда
  `javap -c | awk/grep`, чтобы убрать шум стека (aload/astore/dup/pop) и оставить вызовы, поля, константы, ветвления.
- Почему обходят MCP: (1) классы не из сборки — `tools/*/libs/*.jar`, `build/classes`, `run/.mixin.out` (класс после
  миксинов), jar загрузчика из кеша Gradle; (2) сравнение класса между двумя версиями мода (old/new); (3) «что вызывает
  этот класс» (исходящие ссылки — `code_refs` даёт только входящие); (4) строковые константы класса (ключи перевода).

## Инструмент `bytecode(class*, jar, method, query, diff)` — новый файл `scripts/mcp/tools/disasm.mjs`

Свой разбор (`bytecode.mjs` + собственный декодер инструкций — в `classfile.mjs` нет знаковых смещений переходов,
switch-таблиц и wide), без JDK.

1. **Обзор класса** (без `method`): строка на метод — сигнатура, строки исходника, размер; уникальные вызовы, поля
   (чтение/ЗАПИСЬ), строки и числа. `query` — только методы, где это упоминается. Замена «decompile всего класса»,
   когда нужно просто сориентироваться.
2. **Метод** (`method=` имя или regex): по строкам исходника сжатый поток операций без шума стека: имена локальных
   (LocalVariableTable — добавить разбор в `parseClassFull` как `m.locals`), константы, `.поле` / `→.поле`,
   `Класс.метод()`, `new`, `instanceof`, приведение, арифметика символами, `if< →:47`, `switch{…}`, `return`/`throw`,
   лямбды (`λ lambda$tick$3`, `Foo::bar`), склейка строк.
3. **Внешние источники**: `jar=` ещё и путь к `.jar`, папке классов (`build/classes/java/main`, `run/.mixin.out/class`)
   или `.class`. Поиск класса по полному или простому имени в оглавлении.
4. **Сравнение версий** `diff=<jar или путь>`: с `class` — поля и методы добавлены/удалены/изменены (сравнение потока
   операций без номеров строк), у изменённых — разница вызовов/полей/констант; с `method` — построчный diff потоков
   (LCS). Без `class` — какие классы jar поменялись (CRC из zip, затем нормализованное сравнение, чтобы не считать
   сдвиг строк изменением).

Мелочь в `decompile`: если весь класс длиннее limit и не задан `method`/`grep` — в заголовке подсказать `method=` или
`bytecode`.

## Проверка

Скрипт в scratchpad по stdio к `server.mjs`: обзор и метод на классах TFC (`HeatCapability`), EE, Minecraft;
сравнение с `javap -c` (те же вызовы и константы по методу); внешний источник — `tools/ee-extras-mod/libs/…jar` и
`build/classes`; `diff` — две версии одного jar из `.cache/mcp/fresh` или кандидатов; замер размера ответа против
`decompile` того же метода. Затем `npx oxlint scripts/mcp`, prettier на свои файлы, docs/mcp.md (таблица Mod code),
`INSTRUCTIONS` в `tools.mjs`, docs/state/mcp.md, абзац MCP в CLAUDE.md (вместо javap в терминале — `bytecode`).

## Честно об экономии

Главный путь уже дешёвый: `decompile method=` ~2 тыс. символов. Новый инструмент экономит там, где сейчас агент
выгружает весь класс ради навигации, лезет в терминал за `javap` (внешние jar, сборка аддона, после миксинов) и
сравнивает версии модов руками при обновлении.
