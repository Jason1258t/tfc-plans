# План: программа `tfc` для ПК и сервер сборки

Статус: **этапы 1 и 2 сделаны** (разборщики как библиотека — `npm run pack`; сервер сборки, хранение — `server/pack-server`, 2026-10-20), остальное — план. Вбирает в себя [pack-directory.md](pack-directory.md): «одна команда
на всю папку» и «доставка папки» решаются здесь.

Решения пользователя: сервер сборки — **отдельный Ubuntu-сервер** (как задуманный сервер файлов); программой
пользуются **хост и все игроки**; игроку она докачивает **схемы и датапаки с сайта, моды и конфиги сборки, ресурспаки**.

Главное требование к серверу: **пересобрать данные и обновить Firebase можно с любого рабочего устройства**, без
доступа к ПК с Minecraft. ПК хоста нужен только чтобы залить новую версию сборки (`tfc publish`); всё остальное —
пересборка после правки разборщиков, новые конфиги, выкладка — идёт от сервера.

## Зачем

Сейчас данные сборки живут у того, кто деплоит: jar в `mods/`, архивы конфигов и KubeJS от хоста, четыре отдельные
команды, а сайт деплоится вместе с `public/` этой машины (отсюда грабли с worktree). Игроки ставят схемы, датапаки
и моды руками.

Нужно:

1. **Программа `tfc` на ПК** (Windows / macOS / Linux, сначала командная строка). Ей один раз говорят папку версии
   (инстанс игры или папку сервера) и мир. Дальше она умеет:
   - подтянуть схемы, датапаки и скрипты KubeJS с сайта в нужные папки;
   - сверить моды, конфиги и ресурспаки со сборкой на сервере и докачать недостающее;
   - (хост) залить сборку на сервер и запустить все режимы сборки данных — то, что сейчас `npm run mods/kubejs/serverconfig/world`.
2. **Сервер сборки** — хранит полную сборку (все версии), раздаёт её программе, сам собирает из неё данные сайта
   и обновляет в Firebase только то, что изменилось.

## Как это устроено

```
 ПК хоста (tfc)                 Ubuntu: сервер сборки                     Firebase
 ───────────────                ─────────────────────                     ────────
 tfc publish ──── файлы ───────▶ хранилище (sha256) + снимки сборки
                                  │
                                  ├─ сборка данных (scripts/mods.mjs и др.)
                                  │     │ разница с прошлым снимком
                                  │     ├──────────────▶ Hosting: только изменённые файлы данных
                                  │     └──────────────▶ Firestore: config, packUpdates
 ПК игрока (tfc)                  │
 tfc sync  ◀──── моды, конфиги, ──┤
                 ресурспаки       │
 tfc pull  ◀──── схемы, датапаки, ┴─ читает Firestore/файлы сайта сервисным ключом
                 KubeJS
```

### Почему через сервер, а не прямо в Firebase

- Firestore закрыт App Check (reCAPTCHA): программа без браузера туда не попадёт, а debug-токены на каждого игрока —
  не выход. Сервер ходит в Firebase сервисным ключом, игрокам ключ не нужен.
- 50 тыс. чтений в сутки: синхронизация программ всех игроков не должна их тратить. Сервер кеширует.
- Jar модов (сотни МБ) в Firebase не положить. На сервере — обычный диск.

### Где теперь «источник правды» для данных сайта

Сервер сборки. Тяжёлые данные (предметы, рецепты, иконки, карта) по-прежнему отдаёт **Hosting** — быстро и без
чтений Firestore. Сервер публикует их сам, а деплой сайта с ПК разработчика **скачивает готовые данные с сервера**
вместо сборки из локальных jar (замена `TFC_KEEP_MODS` и грабель с worktree). Firestore — только малое: `config`
и `packUpdates`, как сейчас.

Частичная выкладка Hosting: REST API Firebase Hosting — `versions.clone` текущего релиза без файлов данных,
`populateFiles` с новыми, `finalize`, `releases.create`. Загружаются только файлы с новым хешем. Ключу нужна роль
Firebase Hosting Admin. Если этот путь не взлетит — запасной: сервер запускает `firebase deploy --only hosting`
со своей копией сайта.

### Работа без ПК с Minecraft

Два пути, оба нужны:
- **Пересборка на сервере.** Поменял разборщик в `scripts/` → `git push` → `tfc admin rebuild`: сервер подтягивает
  код, собирает данные из хранимой сборки и публикует только изменённое. Ни jar, ни `firebase login` на рабочей
  машине не нужны.
- **Сборка на рабочей машине.** `tfc fetch` кладёт сборку с сервера в папку проекта (одинаковые файлы не качаются
  повторно), дальше обычные `npm run dev` / `npm run mods` — так проверяют правку разборщика до выкладки.
  Это же снимает грабли worktree без jar.

Новый конфиг сервера без ПК хоста: `tfc config set` делает снимок «текущий + этот файл». Когда хост потом зальёт
сборку со своего ПК, программа покажет расхождение с последним снимком, а не затрёт правку молча.

## Сервер сборки (`server/pack-server`)

Node 22+, без зависимостей (как `server/file-server`), systemd + Caddy, установка `deploy/install.sh <домен>`.
Можно ставить на ту же машину, что и сервер файлов, отдельной службой.

**Хранилище:**
- `blobs/<sha256>` — файлы по содержимому: одинаковый jar в десяти версиях лежит один раз.
- `snapshots/<id>.json` — снимок сборки: `{ id, createdAt, author, note, mc, loader, files: [{ path, sha256, size, kind }] }`,
  `kind` — `mod | config | defaultconfig | serverconfig | kubejs | resourcepack | world-data | world-datapack`
  (вид выводит сервер из пути; файлы мира — под `world/`, без имени мира).
- `channels.json` — какой снимок текущий (`current`); откат — переключить указатель.
- `data/<snapshot>/` — собранные данные сайта для снимка (то, что сейчас `public/*.json`, `icons/` …).

**Доступ — ключи:** у каждого игрока свой ключ (`tfc login`), хост выдаёт их командой `tfc admin invite <ник>`
и может отозвать. Роли: `player` — читать снимки, качать файлы, читать сайт; `admin` — заливать снимки,
переключать текущий, выдавать ключи. Ключи хранятся хешами. Сборка не публичная: моды раздаём только своим.

**API (черновик):**

| Запрос | Кто | Что |
| --- | --- | --- |
| `GET /pack/current` | player | текущий снимок |
| `GET /pack/snapshots`, `GET /pack/snapshots/:id` | player | история, снимок |
| `GET /blobs/:sha256` | player | файл |
| `POST /blobs/missing` | admin | каких файлов из списка нет — заливать только их |
| `PUT /blobs/:sha256` | admin | залить файл (сверка хеша) |
| `POST /pack/snapshots` | admin | создать снимок → запускает сборку данных |
| `POST /pack/current` | admin | сделать снимок текущим (и опубликовать его данные) |
| `GET /site/schematics`, `/site/datapacks`, `/site/kubejs` | player | что есть на сайте (из Firestore, с кешем) |
| `GET /site/files/:id` | player | файл с сайта (исходник схемы, zip датапака) |
| `GET /jobs/:id` | admin | ход сборки данных и публикации (лог) |

## Программа `tfc`

Node, весь код и разборщики — те же `scripts/*.mjs`; для игроков — один исполняемый файл (Node SEA, сборка
esbuild) под Windows, macOS, Linux, Node ставить не нужно. Позже — окно (`tfc ui`: локальная страница в браузере
поверх тех же команд), если командной строки окажется мало.

**Настройка** — `~/.config/tfc/config.json` (Windows — `%APPDATA%\tfc`), несколько профилей:

```jsonc
{ "server": "https://pack.example.com", "token": "…",
  "profiles": { "main": { "instance": "C:/…/instances/TFC RealWorld", "world": "saves/Наш мир", "side": "client" } } }
```

`tfc init` спрашивает папку версии (узнаёт инстансы Prism/MultiMC/CurseForge/лаунчера и папку сервера по
`server.properties`) и предлагает миры из `saves/` (или `level-name` сервера).

**Команды:**

| Команда | Кто | Что делает |
| --- | --- | --- |
| `tfc init`, `tfc login <ключ>` | все | настройка профиля и сервера |
| `tfc status` | все | чем папка отличается от текущей сборки и сайта — ничего не меняет |
| `tfc sync [mods\|config\|resourcepacks]` | все | докачать/обновить из сборки; лишнее — только с подтверждением |
| `tfc pull schematics [имя…]` | все | схемы библиотеки сайта → `<версия>/schematics/` (с заменами и формой, как кнопка «скачать») |
| `tfc pull datapacks [имя…]` | все | датапаки сайта → `<мир>/datapacks/` |
| `tfc pull kubejs` | хост | скрипты с сайта → `<версия>/kubejs/server_scripts/tfc-plans/` |
| `tfc build [mods\|kubejs\|config\|world…]` | хост | все режимы сборки данных локально (то, что `npm run mods` и др.), в `out/` — посмотреть до заливки |
| `tfc publish [--note …]` | хост | залить сборку на сервер (только недостающие файлы), сервер собирает и публикует данные |
| `tfc admin invite/revoke/rollback` | хост | ключи, откат на прошлый снимок |
| `tfc admin rebuild [части]` | разработчик | сервер обновляет свой код (`git pull`), пересобирает данные текущего снимка и публикует разницу |
| `tfc fetch [--into <папка>]` | разработчик | скачать текущую сборку с сервера в папку проекта (`mods/`, `instance/`) — чтобы собирать и проверять на любой машине и в worktree |
| `tfc config set <файл>` | разработчик | поменять конфиг в снимке (новый снимок на основе текущего) и пересобрать — без ПК хоста |

**Правила синхронизации — чтобы не сломать игроку игру:**
- Программа помнит, что сама ставила (`<версия>/.tfc/state.json`: путь → хеш). Удаляет только то, что ставила сама
  и чего больше нет в сборке. Свои моды игрока (миникарта, шейдеры) не трогает, только показывает в `status`.
- Конфиг, который игрок поменял после последней синхронизации, не перезаписывается молча: спрашивает или
  кладёт рядом `*.tfc-new`.
- Перед заменой — копия в `<версия>/.tfc/backup/<дата>/`. `tfc sync --undo` возвращает.
- Пока игра запущена (заблокированный `session.lock` / jar), моды не трогает.
- Клиентская и серверная сборка различаются: снимок заливается с **клиентского** инстанса хоста (что нужно
  игрокам), а данные мира и `serverconfig` — с папки сервера. Профиль хоста может указывать обе.

**Белый список при заливке** — из [pack-directory.md](pack-directory.md): `mods/`, `config/` (без `fancymenu`,
`jmsharedmaps`, `CSC`, `voicechat`, `xaero`, `*.bak`), `defaultconfigs/`, `kubejs/`, `resourcepacks/`,
`<мир>/data/tfc_calendar.dat`, `<мир>/datapacks/`, `logs/latest.log`. **Никогда:** `server.properties`, `ops.json`,
`whitelist.json`, `usercache.json`, `playerdata/`, `stats/`, `region/`, `options.txt`, `servers.dat`.

## Что придётся поменять на сайте

- **Скрипты KubeJS сейчас не хранятся** — конструктор только скачивает файл. Нужна коллекция (`kubejsScripts`:
  имя, текст, автор, «включён»), иначе `tfc pull kubejs` нечего тянуть.
- **Сборщик датапака — общий модуль сайта и Node.** Сам zip — это `pack.mcmeta` + тексты записей; каталог рецептов
  в `lib/datapack.ts` нужен только проверкам. Сборку файлов (`PACK_FORMAT`, `pack.mcmeta`, пути записей, имя zip)
  выносим в `src/lib/datapackFiles.ts` **без импортов** (как `recipeFilter.ts`): на выходе `{ путь: текст }`.
  Сайт зипует это через fflate, сервер и `tfc` — тем же модулем (сервер — клон репозитория, `tfc` — сборка esbuild).
  Отдельный npm-пакет не нужен; понадобится сообществу — модуль уже готов к выносу.
- **Ставим только выбранные датапаки.** Тестовые датапаки на сайте остаются и никуда не ставятся. У датапака
  переключатель «Ставить в мир» (поле `install: boolean`, правила Firestore — вместе с кодом). `tfc pull datapacks`
  без имён ставит только отмеченные; с именем — конкретный (для проверки тестового в одиночном мире). Снятая
  отметка → при следующем `pull` датапак убирается из `<мир>/datapacks/`, но только тот, что ставила сама программа
  (`<мир>/datapacks/tfc-plans-<id>.zip` + запись в `.tfc/state.json`). Пометка «установлен на сервере / отличается»
  на сайте — из снимка сборки (`<мир>/datapacks/`).
- **Схемы — тот же приём.** Сейчас `lib/schematic.ts` тянет поиск замен (fuse.js); применение сохранённых замен
  и формы выносим в модуль без импортов поверх `nbt.ts`, подбор замен остаётся на сайте.
- Раздел «Обновления» — ссылка «как поставить: `tfc sync`».

## Порядок работ

1. **Разборщики как библиотека** (средняя). `mods.mjs`, `kubejs.mjs`, `serverconfig.mjs`, `world.mjs`,
   `pack-release.mjs` принимают папки входа и выхода параметрами, а не от корня репозитория; `firestore-rest.mjs`
   умеет брать токен из сервисного ключа (JWT на `node:crypto`). `npm run pack -- <папка версии> [--world …]` —
   одна команда на всё (этап 1 из pack-directory). Поведение сайта не меняется.
   **Готово (2026-10-20).** `buildMods({ modsDir, outDir, cacheDir, fresh })`, `importKubejsLayer` / `buildKubejs({ instanceDir,
   outDir })`, `configDocs` / `importServerConfig`, `worldDocs` / `importWorld`, `packRelease({ manifestFile, prevFile })`,
   `runPack({ input, world, only, outDir, instanceDir, cacheDir, dryRun })`; запись config — `writeConfigDocs`.
   Токен из сервисного ключа — JWT RS256 на `node:crypto`, проверен на локальной заглушке токен-сервера (подпись,
   поля, кеш); на настоящем ключе Google не проверялся — ключа ещё нет. Выход `npm run mods` и `npm run kubejs`
   до и после — побайтово одинаковый (7574 файла, кроме меток времени `builtAt` / `generatedAt`), и так же — с пустым
   кешем в отдельной папке. `--dry-run` у `pack` в Firestore не пишет, но данные сайта собирает.
2. **Сервер сборки, хранение** (средняя). Хранилище, снимки, ключи, API без сборки данных. Проверка — локально
   (`npm run dev` без Firebase), как сервер файлов. **Сделано** (2026-10-20): `server/pack-server`, README там же.
   Проверено локально node-скриптом: заливка (потоком, сверка хеша, повтор не дублирует, лимит размера), снимки,
   текущий, откат, отказы без ключа / с ключом player на запись / на запрещённые пути и незалитые файлы, выдача
   и отзыв ключей, перезапуск. **На Ubuntu `install.sh` не запускался.** Отличия от черновика выше:
   - `logs/latest.log` в снимок не берётся: снимок раздаётся игрокам, а в логе сервера — их адреса. Лог для
     сборки данных (этап 4/7) — отдельной заливкой, только для admin.
   - Добавлен вид `serverconfig`; `parent` в снимке — какой снимок был текущим при создании (для `tfc config set`).
   - Первый admin-ключ — `cli.mjs key add` (его зовёт `install.sh`), им же — восстановление при потере.
   - Caddy: у каждой службы свой блок в `/etc/caddy/conf.d/` (`server/common/caddy-site.sh`), install.sh сервера
     файлов переведён на то же — иначе две службы на одной машине затирали бы `Caddyfile` друг друга.
   - Не сделано: удаление старых снимков и чистка неиспользуемых файлов (место пока не жмёт).
3. **`tfc`: настройка, `status`, `publish`, `sync`** (большая). Заливка недостающего, синхронизация по правилам выше.
   Проверка — на копиях инстанса в scratchpad.
4. **Сборка и публикация на сервере** (большая). Задание сборки после снимка и по `tfc admin rebuild`, разница
   с прошлыми данными, частичная выкладка Hosting, `config` и `packUpdates`. `tfc fetch`; деплой сайта берёт данные
   с сервера.
5. **Контент сайта в `tfc pull`** (средняя). Общие модули сборки датапака и схемы, отметка «Ставить в мир»,
   коллекция скриптов KubeJS. Вынос `datapackFiles.ts` можно сделать раньше — он ни от чего не зависит.
6. **Сборка в один файл под Windows/macOS/Linux, инструкция для игроков** (малая–средняя).
7. Потом: `tfc ui`, ошибки из `logs/latest.log` к датапакам сайта, квесты, сид из `level.dat` (из pack-directory).

Этапы 1 и 2 независимы, их можно делать параллельно. 3 ждёт 2; 4 ждёт 1 и 2.

## Что нужно от пользователя

- Ubuntu-сервер и домен (поддомен) под сервер сборки — можно тот же, что для сервера файлов. Место на диске:
  сборка ≈ 0,5 ГБ, плюс по ~50–100 МБ на обновление (одинаковые jar не дублируются).
- Сервисный ключ Firebase с ролями Cloud Datastore User и Firebase Hosting Admin (создаётся в консоли, кладётся
  только на сервер).
- Проверка на Windows: исполняемый файл и пути инстанса у хоста и игроков агент проверить не может.

## Правила, которые не меняются

- Всё, что показывает сайт, достаётся скриптом из файлов сборки; руками ничего не вписывается.
- Коллекцию `config` читает любой посетитель: туда — только используемое, без секретов и личного.
- Сервисный ключ и ключи игроков — только на сервере и в настройках программы, не в git и не на сайте.
