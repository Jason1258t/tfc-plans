# План: обновления сборки, патчноуты от модели, справочник руд

Статус: **все этапы сделаны** (2026-10-07). Решения по вопросам: патчноут пишется автоматически при первом открытии
свежего обновления; ченджлоги Modrinth включены; в шапке точка «новое»; справочник — руды, топливо, еда, металлы.
Первая запись («Начало истории») создана при деплое 2026-10-07.

## Зачем

Сборку время от времени обновляют: дропают новые jar в `mods/` и деплоят. Что при этом изменилось, сейчас не видно. Новые предметы, пропавшие рецепты, сломанные датапаки и типы рецептов без подсказок всплывают только в игре или в логе сервера.

Нужно, чтобы каждое обновление сборки оставляло на сайте запись. В ней:
- машинная разница (что добавилось, убралось, поменялось);
- предупреждения о датапаках, которые могли сломаться;
- **патчноут от модели** — человеческий текст «что нового и что это значит для нас».

Плюс справочник руд — его данные берутся тем же путём.

## Как устроено сейчас

- `npm run items` (`scripts/build-items.mjs`) собирает из jar `public/items.json`, `public/recipes.json` и иконки. Файлы в git не хранятся, собираются у того, кто деплоит.
- `ensure-items` перед `dev` и `build` пересобирает библиотеку, если поменялись jar. Подпись jar лежит в `.cache/items-signature.json`, это имя, размер и дата файла.
- Подсказки по рецептам, датапаки и файлы лежат в Firestore. Агент — Gemini через AI Logic в браузере.

## Этап 1. Снимок сборки

`build-items.mjs` дополнительно пишет `public/pack-manifest.json` — компактный отпечаток сборки:

```jsonc
{
  "builtAt": 1791300000000,
  "mods": [{ "id": "tfc", "name": "TerraFirmaCraft", "version": "4.2.9", "jar": "TerraFirmaCraft-NeoForge-1.21.1-4.2.9.jar", "sha1": "…" }],
  "items": ["tfc:metal/ingot/copper", …],      // только id
  "recipes": { "tfc:heating/…": "a1b2c3", … },  // id → короткий хеш JSON — ловит изменённые рецепты
  "recipeTypes": ["tfc:heating", …]
}
```

- `id`, название и версия мода берутся из `META-INF/neoforge.mods.toml`. Если там `${file.jarVersion}`, версия берётся из `MANIFEST.MF`.
- `sha1` jar нужен на этапе 4, чтобы найти мод на Modrinth.
- Ожидаемый размер — около 1,5 МБ, сжатый около 300 КБ. Грузится только на странице обновлений.

## Этап 2. Запись об обновлении при деплое

Скрипт `scripts/pack-release.mjs` встраивается в `npm run deploy` перед `firebase deploy` и работает так:

1. Скачивает **текущий опубликованный** `https://tfc-plans-fd2c.web.app/pack-manifest.json` — это и есть «прошлая версия». Отдельно хранить историю снимков не нужно.
2. Сравнивает его с локальным `public/pack-manifest.json`. Если отличий нет, ничего не делает.
3. Если отличия есть, пишет в Firestore документ `packUpdates/{id}`, где id — хеш нового снимка, так что повторный деплой не создаёт дублей:

```ts
interface PackUpdate {
  id: string;
  createdAt: number;
  deployedBy: string;           // ник из .env.local или git user.name
  mods: {
    added: ModRef[];
    removed: ModRef[];
    updated: { id: string; name: string; from: string; to: string }[];
  };
  items: { added: string[]; removed: string[] };       // списки урезаны до 3000, точные счётчики — отдельно
  recipes: { added: string[]; removed: string[]; changed: string[] };
  counts: { items: [number, number]; recipes: [number, number] }; // было → стало
  newRecipeTypes: string[];
  changelogs?: Record<string, string>; // этап 4
  notes?: { body: string; source: 'agent' | 'manual'; updatedBy: string; updatedAt: number }; // этап 5
}
```

Запись идёт от имени залогиненного firebase CLI — так же, как уже работает `seed-recipe-hints.mjs`. Если документ больше 1 МиБ (бывает при огромном обновлении), полные списки уходят файлом в хранилище файлов — пакет `firestore-files`, когда сайт на него переедет. Пока списки просто урезаются.

Первый деплой после внедрения создаёт «нулевую» запись: прошлого снимка на хостинге ещё нет. Она показывается как «начало истории» со списком модов.

## Этап 3. Страница «Обновления» (`/updates`)

Лента обновлений, новые сверху. В карточке обновления:

- **Патчноут от модели** вверху — главное (этап 5).
- **Моды**: добавленные, убранные и обновлённые с версиями «было → стало». Если есть ченджлог — раскрывается.
- **Предметы**: новые и пропавшие, сгруппированные по модам, с иконками. Пропавшие иконки берутся из старого снимка — проще показывать их по id без картинки.
- **Рецепты**: добавленные, удалённые и изменённые с разбивкой по типам. Клик открывает каталог рецептов на этом рецепте.
- **Новые типы рецептов без подсказок** — кнопка «составить агентом». Механизм тот же, что в редакторе датапаков.
- **Под угрозой**:
  - датапаки сайта, которые ссылаются на исчезнувшие предметы;
  - датапаки, которые заменяют или удаляют рецепты, исчезнувшие или изменившиеся в сборке.

  Для отслеживания изменений в записи датапака сохраняется хеш исходного рецепта (`DatapackEntry.sourceHash`) в момент, когда его взяли за основу. У старых записей хеша нет — для них проверяется только существование рецепта.

Те же проверки датапаков работают и без обновления — плашкой на странице датапака: «2 записи ссылаются на то, чего нет в текущей сборке».

## Этап 4. Ченджлоги модов с Modrinth (по желанию)

В `pack-release.mjs`, только для обновлённых модов:

- `POST https://api.modrinth.com/v2/version_files` со списком sha1 jar. Ключ не нужен, лимит 300 запросов в минуту, нужен заголовок `User-Agent`. В ответе найденные версии с полем `changelog` (markdown).
- Моды, которых нет на Modrinth (только CurseForge — там API требует ключ, или кастомные jar), остаются без ченджлога. Это видно в карточке.
- Ченджлоги обрезаются до разумного размера: около 4 000 символов на мод.

Этот этап сильно улучшает патчноуты: модель пересказывает настоящие изменения, а не угадывает по списку id.

## Этап 5. Патчноут от модели

- Генерируется при первом открытии обновления (если `notes` ещё нет) или кнопкой «Обновить агентом». Это **один запрос**, как с подсказками. Результат сохраняется в `notes`, его можно править руками (`source: 'manual'`).
- Вход модели:
  - изменения модов с версиями;
  - ченджлоги, если есть;
  - счётчики;
  - выборка предметов и рецептов: новые типы, по 30 примеров на мод с ru-названиями;
  - предупреждения о датапаках;
  - контекст: «это TFC-сборка группы, у нас есть задачи в группах …».
- Выход: markdown на русском в 3–4 разделах — «Главное», «Новое», «Что проверить в наших задачах и датапаках», «Мелочи». Модели запрещено выдумывать: только то, что есть во входе, а разделы без данных она пропускает.
- Модели: `CHAT_MODELS` с откатом, как сейчас. Бесплатного дневного лимита на редкие обновления хватает с запасом.

## Этап 6. Справочник руд (`/ores`)

Данные — конфиги жил `data/*/worldgen/configured_feature/vein/*.json`. В сборке их 67:
- TFC — 52;
- TFC-IE-Crossover — 5;
- Beneath — 7 (Незер);
- Firmalife — 2;
- IE — 1.

Собираются в `public/veins.json` тем же скриптом. Более поздние источники перекрывают ранние, как с рецептами.

- **Поля**: тип жилы (cluster, pipe, disc), редкость, плотность, размер, `min_y`/`max_y`, в каких породах встречается, доли бедной, нормальной и богатой руды, индикатор на поверхности.
- **Страница**:
  - поиск по руде или металлу («олово» → касситерит);
  - фильтр по породе — «что искать в граните» — в обе стороны;
  - таблица с иконками;
  - полоска высот;
  - клик по руде открывает её рецепты нагрева и что из неё получается.
- **Оговорка**. Это данные из jar. Если на сервере жилы переопределены датапаком или KubeJS, справочник это не увидит — так же, как каталог рецептов.

Попутно, тем же способом и почти бесплатно — **топливо** (`tfc/fuel`, 53 записи: температура и время горения) и **еда** (`tfc/food`, около 200: питательность и скорость порчи). Это отдельные таблицы на той же странице «Справочник».

## Объём и порядок

| Этап | Оценка | Зависит от |
|---|---|---|
| 1. Снимок сборки | мало | — |
| 2. Запись при деплое | мало–средне | 1 |
| 3. Страница обновлений и проверки датапаков | средне | 2 |
| 4. Ченджлоги Modrinth | мало | 2 |
| 5. Патчноут от модели | мало | 3 (лучше с 4) |
| 6. Справочник руд, топлива и еды | средне | — (только скрипт сборки) |

Порядок: 1 → 2 → 3 → 5, затем 4 и 6. Справочник независим, его можно делать параллельно или первым, если он нужнее.

## Вопросы

1. **Кто деплоит обновления сборки?** План предполагает, что `npm run deploy` запускают вы со своей машины, где лежат `mods/` и есть `firebase login`. Если деплоить будет кто-то ещё, ему понадобится `firebase login` с доступом к проекту.
2. **Генерация патчноута**: автоматически при первом открытии или только по кнопке? Предлагаю автоматически: тогда патчноут уже готов, когда его откроют остальные.
3. **Ченджлоги с Modrinth** — включаем? Это единственный внешний запрос в процессе деплоя.
4. **Уведомления.** Нужна ли метка «новое обновление» в шапке сайта для тех, кто ещё не видел? Хранится локально в браузере, без аккаунтов.
5. **Справочник**: только руды, или сразу добавить топливо и еду?

## Не входит

- Сравнение с конфигами и скриптами сервера (`config/`, `kubejs/`). Сайт видит только jar. Если когда-нибудь появится доступ к серверу, это отдельная задача.
- История обновлений до внедрения: первая запись станет точкой отсчёта.
